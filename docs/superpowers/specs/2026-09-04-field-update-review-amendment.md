# Review amendment: field update and automatic updates

This amendment is part of `2026-09-04-field-update-and-auto-update-design.md` and supersedes its conflicting wording.

1. New installers use the exact name `KRS-AcquiringMonitor-<version>-setup.exe`. The historical 0.1.0 filename is not supported by the automatic-update contract because 0.1.0 contains no updater. Each installed 0.1.0 copy requires one manual upgrade to 0.2.0; automatic updates begin with 0.2.0.
2. The Inno Setup run entry does not use `skipifsilent`, so the application starts after both interactive installation and a silent update.
3. The installer download URL is exactly `https://github.com/jadieify-hub/krs-acquiring-monitor/releases/download/v<version>/KRS-AcquiringMonitor-<version>-setup.exe`.
4. `update.json` contains only `version` and `sha256`. `filename` is removed because it is fully derived from the validated version and provides no independent security barrier.
5. The release script parameter is the authoritative version for a release. It passes the version to MSBuild and ISCC. Values in `Directory.Build.props` and the Inno script remain development fallbacks. Runtime UI and logging read the executing assembly version rather than a separate `AppConstants.Version` literal.
6. `ShadowTextControl.cs` is removed. The replacement draws plain white overlay text once and retains only the minimum hit-testing required for dragging and refresh.
7. The amber refresh indication carries exactly one meaning: the displayed totals are not current. Stale data after a settlement and a deferred request both use it, so a cashier never has to tell two amber states apart. Row text always uses the configured text colour. Implemented.
8. The update check is periodic rather than once per process start: the first check runs shortly after the UI appears and repeats every six hours. Installation is additionally gated on the bank journal being quiet — no unfinished operation and no journal change for thirty seconds — so a periodic check cannot remove the overlay during a transaction. This replaces the earlier one-shot wording and the risk window it was meant to avoid. Implemented.
9. Automatic organization naming must stop asking the terminal. One accepted unambiguous report ends the background attempts permanently, because a statistics report lists every organization configured on the terminal and not only those with transactions in the current shift. Failed or rejected attempts are capped at three per process start, after which naming continues only on an explicit manual refresh. Implemented.
10. A background naming request never starts while any application window is open, and a request already running blocks the settings and the data reset until it finishes. The cashier therefore never competes with a background request for the settings dialog. Implemented.
11. The overlay has no resize grip. Width comes from automatic fitting or from the settings field, as item 13 describes, never from a mouse gesture; dragging by an organization name still moves the overlay. The trailing margin that the grip used to occupy is preserved so a stored width still produces the same overlay width.
12. Release verification includes retaking `docs/screenshots/overlay.png` whenever the overlay changes. This is a manual step that no automated test covers.
13. Overlay width fits the longest organization name automatically, so a name is never trimmed to an ellipsis, and stays inside the range the settings field allows. A width typed into the settings field turns fitting off and survives every later total, refresh and restart; it is released only when the set of displayed organizations changes, which includes a rename, because a different name needs a different width. The decision is one place, `AppSettings.TryUpdateOverlayWidthSignature`. Amounts are measured as before, so an amount growing by a digit can still change the fitted width during a shift.
14. Settlement resets every organization on a single successful `close_day` result (`Command = 6000`). This supersedes the two-close rule in the "Shift-close correction" section of `2026-09-04-field-update-and-auto-update-design.md` and in `2026-09-04-krs-acquiring-monitor-design.md`: UPOS closes the whole terminal in one call, so waiting for a second close left the totals standing for the rest of the shift whenever only one close ever arrived. A failed close still counts for nothing. A statistics result (`Command = 7000`) never resets anything and ends the wait for a close instead of leaving the monitor pending, because the terminal has answered and is idle again. Implemented in 0.2.12 and later.
15. The silent self-update starts the installer with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /NOCLOSEAPPLICATIONS /NORESTARTAPPLICATIONS /SP-` plus `/WAITPID=`, `/DIR=` and `/LOG=`, not the `/CLOSEAPPLICATIONS` of the design document and the plan. The monitor exits on its own and passes its own process id, so the installer waits for that instead of spending twenty-five to thirty seconds scanning for applications to close, and must not restart anything because the installer's own run entry starts the new copy. An interactive installation over a running copy still closes it, through `CloseApplications=force` and `CloseApplicationsFilter` in the installer script. Implemented.
